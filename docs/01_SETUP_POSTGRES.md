# PostgreSQL: конфигурация и загрузка данных

Как поднять базу под датасет KKBox и залить в неё 392 млн строк.

Инструкция написана под конкретное железо: **Windows, PostgreSQL 18, pgAdmin 4, 32 ГБ RAM, 12 ядер / 24 потока.** База лежит на SSD, исходные CSV — на отдельном HDD. Это удачная раскладка: во время загрузки один диск только читает исходники, другой только пишет базу, и они не мешают друг другу.

Порядок получения данных и контрольные суммы — в [`DATA.md`](../DATA.md).

---

## 1. Инструменты

PostgreSQL — это сервер: он хранит данные и выполняет запросы, но своего интерфейса у него нет. Работать с ним нужно через клиент, и здесь используются оба доступных:

| Инструмент | Что это | Для чего здесь |
|---|---|---|
| **psql** | консольный клиент, ставится вместе с сервером | загрузка CSV, в том числе файла на 30 ГБ |
| **pgAdmin 4** | графический клиент | запросы и просмотр результатов |

Долгую загрузку удобнее вести из psql: видно время каждой команды и прогресс. Смотреть результат запроса из сотни строк удобнее в pgAdmin.

**PostGIS не нужен.** В KKBox нет координат: география представлена колонкой `city` — целочисленный код без расшифровки.

## 2. База и схемы

```sql
CREATE DATABASE churn_case;
```

Затем, подключившись к ней:

```sql
CREATE SCHEMA raw;      -- сырые данные как есть
CREATE SCHEMA staging;  -- очищенные и типизированные
CREATE SCHEMA marts;    -- витрины под конкретные вопросы
```

То же самое — [`../sql/setup/00_schemas.sql`](../sql/setup/00_schemas.sql).

**Зачем три слоя.** Сырой слой неприкосновенен: ошибка в трансформации чинится пересборкой `staging`, а не повторной заливкой 30 ГБ CSV.

Граница проведена жёстко: в `raw` данные лежат ровно как в файле — даты остаются целыми числами `YYYYMMDD`, пустые значения остаются пустыми. **Вся интерпретация происходит в `staging` и только там.**

## 3. Конфигурация под 32 ГБ и SSD

Настройки по умолчанию рассчитаны на минимальную машину: `shared_buffers` 128 МБ, `work_mem` 4 МБ.

Где лежит конфигурация, показывает сам сервер:

```sql
SHOW data_directory;
```

Файл `postgresql.conf` лежит в этой папке. Параметры можно править текстовым редактором (от имени администратора) либо задавать командами `ALTER SYSTEM SET ...` — второй путь надёжнее, потому что неверное значение отвергается сразу с понятной ошибкой.

```conf
# --- Память ---
shared_buffers = 2GB
effective_cache_size = 24GB
maintenance_work_mem = 2GB
work_mem = 128MB

# --- Параллелизм (12 физических ядер) ---
max_worker_processes = 24
max_parallel_workers = 12
max_parallel_workers_per_gather = 4
max_parallel_maintenance_workers = 4

# --- Запись: ускоряет массовую загрузку ---
max_wal_size = 16GB
min_wal_size = 2GB
checkpoint_timeout = 60min
checkpoint_completion_target = 0.9

# --- Диск: значения для SSD ---
random_page_cost = 1.1
effective_io_concurrency = 200
```

**`shared_buffers = 2GB`, а не 8.** На Linux для такой машины ставят четверть памяти, но Windows работает с разделяемой памятью иначе, и после ~2 ГБ выигрыш пропадает, а иногда становится хуже. Основное кэширование на Windows делает сама ОС — поэтому `effective_cache_size` выставлен щедро: это не выделение памяти, а подсказка планировщику, сколько данных вероятно окажется в кэше.

**`work_mem = 128MB`** — лимит на одну операцию сортировки, а не на запрос. Запрос с тремя сортировками и четырьмя параллельными воркерами может занять 128 × 3 × 4 ≈ 1,5 ГБ. Для тяжёлого запроса значение поднимается в сессии: `SET work_mem = '512MB';`

**`random_page_cost = 1.1`** — значение для SSD. Это не скорость, а относительная стоимость: во сколько раз случайное чтение дороже последовательного. У SSD нет движущихся головок, поэтому разница почти отсутствует, и планировщику нужно об этом сказать — иначе он будет избегать индексов там, где они выгодны. На механическом диске здесь ставят 4.

**`checkpoint_timeout = 60min` и `max_wal_size = 16GB`** подняты ради массовой загрузки. Контрольная точка — сброс накопленных изменений на диск; чем реже она случается во время заливки 392 млн строк, тем ровнее идёт запись. Плата — дольше восстановление после аварийного выключения, для аналитической базы это неважно.

После правки служба перезапускается, и применение проверяется:

```sql
SELECT name, setting, unit FROM pg_settings
WHERE name IN ('shared_buffers', 'work_mem', 'random_page_cost');
```

## 4. Таблицы сырого слоя

Семь CSV — семь таблиц, зеркально. Файлы `_v2` грузятся отдельно от основных; объединяются в `staging`.

Полный скрипт — [`../sql/setup/01_create_raw.sql`](../sql/setup/01_create_raw.sql). Ключевые решения:

**Даты остаются `integer`.** В файле написано `20150930` — это и есть содержимое. Приведение к `date` было бы интерпретацией, а её место в `staging`. Побочный плюс: секционирование по целому числу работает так же хорошо, как по дате.

**`total_secs` — `double precision`, а не `numeric` с ограничением.** В колонке есть отрицательные значения и абсурдно большие (порядка 10⁹ секунд — 30 лет прослушивания за сутки). Строгий тип не дал бы им загрузиться, и строки потерялись бы молча. Грязь доезжает до `raw` целиком и отбраковывается осознанно в `staging`, с подсчётом отброшенного.

**`user_logs` секционирована по месяцам.** Секционирование режет таблицу на куски по значению колонки: снаружи она выглядит одной таблицей, но планировщик читает только нужные куски (partition pruning). Без этого любой запрос за отдельный месяц читал бы все 392 млн строк.

Секции создаются генератором — 28 месяцев на каждую из двух таблиц логов, 56 штук:

```sql
DO $$
DECLARE
    t   text;
    d   date;
BEGIN
    FOREACH t IN ARRAY ARRAY['user_logs', 'user_logs_v2'] LOOP
        d := date '2015-01-01';
        WHILE d < date '2017-05-01' LOOP
            EXECUTE format(
                'CREATE TABLE raw.%I PARTITION OF raw.%I
                 FOR VALUES FROM (%s) TO (%s)',
                t || '_' || to_char(d, 'YYYYMM'), t,
                to_char(d, 'YYYYMMDD'),
                to_char(d + interval '1 month', 'YYYYMMDD')
            );
            d := d + interval '1 month';
        END LOOP;
    END LOOP;
END $$;
```

## 5. Загрузка

**Индексы создаются после загрузки, не до.** Иначе каждый индекс перестраивался бы на каждой вставленной строке.

**Используется `\copy`, а не `COPY`.** Серверный `COPY` читает файл силами процесса PostgreSQL, а служба на Windows работает под системной учётной записью, у которой нет доступа к пользовательским папкам. `\copy` — клиентская команда psql: файл читает psql и передаёт серверу потоком.

Скрипт — [`../sql/setup/02_load_raw.sql`](../sql/setup/02_load_raw.sql). Мелкие файлы идут первыми, чтобы ошибка в схеме всплыла до загрузки логов. Пути к CSV в скрипте относительные, поэтому он запускается из папки с данными:

```powershell
cd D:\proj\churn-pm-case\data
psql -U postgres -d churn_case -f ..\sql\setup\02_load_raw.sql
```

## 6. Сверка

Обязательный шаг. Число строк в базе сверяется с числом строк в файлах (за вычетом заголовка) — эталон в [`DATA.md`](../DATA.md), раздел 4.

Без этой проверки оборванная загрузка не ловится: запросы будут работать, просто на неполных данных, и все дальнейшие выводы окажутся неверными.

Скрипт — [`../sql/setup/03_verify_raw.sql`](../sql/setup/03_verify_raw.sql). Он же проверяет горизонт данных: максимальная дата в `transactions_v2` и `user_logs_v2` должна быть `20170331`, а апрельские секции логов — пустыми.

## 7. Индексы и статистика

Скрипт — [`../sql/setup/04_raw_indexes.sql`](../sql/setup/04_raw_indexes.sql): `UNIQUE` на `train`, `train_v2` и `members`, обычные индексы по `msno` на транзакциях и логах, затем `VACUUM ANALYZE`.

Индекс на `user_logs (msno)` сначала казался слишком дорогим: оценка была ~25 ГБ. На деле он занял 4,3 ГБ — с PostgreSQL 13 B-tree сжимает повторяющиеся ключи, а у каждого пользователя в логах десятки строк. Составной `(msno, date)` не строится: там такого сжатия нет.

`UNIQUE` на `train` и `members` — ещё и проверка: если индекс не создаётся из-за дубликатов, значит в файле есть повторы `msno`, и это находка, которую нужно зафиксировать до того, как она испортит джойны.

`VACUUM ANALYZE` обязателен. Без него планировщик работает по пустой статистике и выбирает заведомо плохие планы — например, вложенный цикл там, где нужен hash join.

## 8. Слой staging

Здесь `YYYYMMDD` становится датой, `_v2` объединяется с основными таблицами, а грязь отбраковывается — с подсчётом, сколько строк ушло по каждому правилу. Файлы — в [`../sql/setup/`](../sql/setup/), порядок важен.

| Файл | Таблица | Что делается |
|---|---|---|
| `05` | `staging.members` | дата регистрации из int, возраст вне 13–75 → `NULL` |
| `06` | `staging.transactions` | `UNION` основной таблицы и `_v2`, даты из int, восстановление незаписанного тарифа по сумме оплаты |
| `07` | `staging.labels` | метка оттока из `train` |
| `08` | `staging.label_recalc` | независимый пересчёт метки по опубликованному коду разметки — строится до `09` |
| `09` | `staging.transactions` | удаление 9 717 транзакций с невозможной датой окончания подписки |
| `10` | `staging.user_logs_monthly` | логи, свёрнутые до «пользователь × месяц», три правила очистки `total_secs` |
| `11` | `staging.subscription_episodes` | эпизоды подписки: перерыв 30+ дней — уход, возвращение — новый эпизод |
| `99` | — | контрольные числа всего слоя |

Приведение целого к дате:

```sql
to_date(transaction_date::text, 'YYYYMMDD')
```
